# 细粒度三源章节生成

## 目标

章节生成不再把整章所有材料一次性塞入模型，而是先优化目录节点，再按语义拆成 1 至 4 个写作单元。每个单元独立匹配投标证据、优秀施组原子和写作组织技巧，最后由程序装配为一个可追溯章节。

三类输入职责严格分开：

1. 投标证据是项目名称、范围、工程量、参数、日期、规范、审批和管理责任等事实的唯一来源。
2. 参考原子只提供异项目的工序展开、控制维度、检查闭环和专业表达。
3. 写作技巧只规定章节顺序、要点覆盖和表达方式，不提供项目事实。

## 目录优化

`plan_template_outline.py` 在目录规划后为节点补充：

- `generation_role`：容器节点或可生成叶子节点。
- `coverage_status`：投标来源覆盖情况。
- `writing_unit_hints`：建议拆分的写作主题。
- `generated_overview`、`established_facts`、`interfaces`、`terminology` 和 `unresolved_items`：生成后的滚动概括。

Markdown 章节解析使用源文件、标题路径和起始行生成稳定且唯一的 `section_id`。形如 `8 线：110kV...` 的工程数量行会被排除，避免成为后续技术条款的错误父标题。

## 写作单元

`chapter_writing_units.py` 根据目标字数、生成策略和章节主题生成 `WritingUnitSpec`。正文较密的工艺章节通常拆为：

- 适用范围、施工准备与资源条件。
- 工艺流程、施工方法与参数控制。
- 质量检查、试验验收与记录。
- 安全环保、风险防控与异常处置。

单元目标控制在约 350 至 850 字。每个单元只携带命中的来源章节和证据片段，上一单元仅以压缩概括传给下一单元，减少重复和上下文噪声。

生成前可查看：

```http
GET /projects/{project_id}/chapters/{node_id}/writing-units
```

## 高相关原子匹配

原子召回采用两阶段约束：

1. 硬过滤：只允许 `published` 原子，排除当前项目和同名项目，并按爆破、开挖、支护、混凝土、灌浆、导流、填筑和金属结构等技术族过滤。
2. AI 重排：模型根据工程对象、工序、适用条件和当前单元证据评分；低于 `0.62` 的结果被程序再次拒绝。

系统明确禁止仅以“控制闭环可类比”为理由跨工序补齐数量。例如爆破单元不能召回喷射混凝土或泌水处理原子。每个单元最多使用 3 条，宁缺毋滥。

`WritingUnitTrace` 保存本次实际使用的：

- `source_section_ids`
- `evidence_ids`
- `reference_atom_ids`
- `writing_skill_keys`
- `prompt_source_roles`

## 全局与章节概括

`GenerationContextState` 保存项目概述、施工范围、确认事实、统一术语、施工接口、待确认项和已生成章节顺序。每章完成后生成 `ChapterRollingSummary`，下一章只接收压缩后的最近章节概括。

事实防扩散规则：

- 内容概述可以概括已生成正文。
- 术语可以从正文提取。
- `established_facts`、全局事实和跨章节接口必须同时得到当前投标证据支持。
- 生成正文不能反向为自身提供事实证明。

生成上下文可查看：

```http
GET /projects/{project_id}/generation-context
```

持久化文件：

- `control/writing-units/{node_id}.json`
- `context/generation_context.json`
- 章节版本的 `generation_metadata.json`
- LLM trace 目录中的各写作单元提示词与响应

## 输出与审计

程序将多个单元装配为固定结构：

```markdown
# 章节标题

## 主要来源摘要

## 生成正文

### 写作单元一

### 写作单元二

## 人工补充需补充
```

来源摘要仅展示各写作单元实际选中的 `section_id` 和 `evidence_id`，不会再罗列整章映射中的旁支来源。提示词还禁止在证据缺失时自行增加管理主体、审批机关、许可手续、库房设置、人员资质、检查频次和验收责任。

数值、地名、工程量、设备数量、日期和规范版本继续执行参考原子泄漏审计；命中异项目专属值时自动删除、定性改写或转为人工补充占位。

## 用户体验闭环

首版不追求把所有技术判断自动化到极致，质量控制收束为三条底线：项目事实不凭空扩写、三类依据职责清楚、生成结果可以追溯。其余能力优先服务于流程顺畅和用户可控。

### 项目状态总览

工作台顶部持续展示当前阶段、已索引资料、目录节点、生成进度和原子库状态，并给出一个明确的下一步动作。用户不需要理解内部任务状态，也能知道目前做到哪里、接下来点击什么。

```http
GET /projects/{project_id}/experience-summary
```

### 目录反馈改良

目录树在节点旁展示来源覆盖状态，选中节点后展示本章用途、范围、写作提示和待确认事项。用户可以使用常见反馈快捷项，也可以输入自然语言要求。AI 只生成可预览的目录修改方案，用户确认后才应用，不直接覆盖当前目录。

常用反馈包括补足工艺层级、合并重复章节、补齐质量安全验收闭环，以及依据投标目录纠正标题和归属。修改后重新生成节点概括，使后续章节生成始终使用最新目录意图。

### 生成前可信预览

选中章节后先展示三类依据及各自用途：

- 投标文档决定本项目事实，并展示候选标题路径。
- 优质原子只补充工序组织和控制闭环；没有高相关原子时明确说明不强行使用。
- 写作技巧控制结构和表达，不作为事实来源。

同时展示本章计划拆成几次模型调用、每个写作单元的主题和目标字数。该预览不调用生成模型，用户可以先判断依据是否可靠，再决定是否生成。

```http
GET /projects/{project_id}/chapters/{node_id}/writing-units
```

生成完成后才展示版本凭据，包括实际写作单元、投标证据、参考原子和写作技巧数量。预览回答“准备怎么写”，版本凭据回答“刚才依据什么写”，避免空状态和历史版本信息混淆。

### 原子库友好流程

优秀施组与当前投标资料分库存储。页面将流程固定为“上传优秀施组 -> AI 自动切分与标注 -> 人工快速抽查 -> 发布后参与生成”，候选原子默认不发布。用户可逐条发布或排除，不需要先理解向量索引、标签体系和检索分数。

```http
GET  /reference-library/summary
POST /reference-library/upload-markdown
PATCH /reference-library/atoms/{atom_id}/status
```

参考库为空、切分失败或没有高相关原子时，章节生成仍可依据投标证据和写作技巧继续。系统给出降级说明而不是中断流程，以便用户先完成工作、以后再逐步丰富原子库。
